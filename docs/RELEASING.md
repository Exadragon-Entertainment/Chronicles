# Release and Versioning Guide

Chronicles and ChronData use a modified version of Semantic Versioning (SemVer 2.0.0) to handle our game versions, development stages, and internal API version.
ChronCompiler uses the same format, but with API version replaced with DB format version.

## Version Format
All user-facing version strings follow this pattern:
`MAJOR.MINOR.PATCH-STAGE.BUILD+api.API_VERSION`

* **Game Version (`MAJOR.MINOR.PATCH`)**: Incremented based on game features and bug fixes.
* **Pre-release Stage (`-STAGE.BUILD`)**: Tracks testing phases. Previews **must** use a numeric digit so they sort before Alphas.
  * Preview: `-0.0`, `-0.1`
  * Alpha: `-a.0`, `-a.1`
  * Beta: `-b.0`, `-b.1`
  * Release Candidate: `-rc.0`, `-rc.1`
  * Release: omitted
* **API (`+api.API_VERSION`)**: Appended as build metadata (e.g., `+api.59`).

### Notice on API Updates
Any change to the Modding API **forces at least a PATCH increment** in the game version. Never increment the API number without increasing the game version number.

### Notice on ChronCompiler
The DB version generated by ChronCompiler is used in place of the api version (e.g., `+tdb.12`). Changing this or the DB format **forces at least a PATCH increment**.

## Windows Resource Files (`*.rc`)
Windows resource file fields `FILEVERSION` and `PRODUCTVERSION` do not accept text strings. You must translate the version into a 4-part numeric code: `MAJOR,MINOR,PATCH,BUILD`

Calculate the 4th numeral `BUILD` using this formula: 
`[Stage Prefix * 10,000] + [BUILD]`

API/DB version is omitted from this field because any bump to the api version forces a change in at least the patch number. Including the API version in the user-facing string
is done so for ease of use and github tag/release navigation, not because it is strictly necessary.

### Stage Prefix Keys:
* Preview = `1`
* Alpha = `2`
* Beta = `3`
* RC = `4`
* Stable = `5`

### Example Mapping:
* **Version String:** `0.1.2-a.1+api.59`
* **RC Binary Configuration:** `FILEVERSION 0,1,2,20001`
